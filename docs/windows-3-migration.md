# Windows 3.0 production migration

Build with `pnpm dist:win` / `scripts/build-windows-artifacts.mjs`. The wrapper enables migration only for `cc.jiwo.arkme` and refuses `ARKME_WINDOWS_ALLOW_UNSIGNED=1`. Test builds use the existing include without the production define and retain their original behavior. Do not publish a production installer produced by a direct `electron-builder` invocation: it bypasses the migration wrapper.

Identity remains `arkme.exe` and NSIS GUID `14ace15a-7c69-5467-bedd-7df6c628d51a` (explicitly retained from the old appId; the application AUMID is now `cc.jiwo.arkme`). Existing Electron installations keep the same upgrade registration, scope, and directory; the installer replaces builder’s uninstall-first path with a file-level recovery journal. Flutter identification is exclusively the exact Inno AppId `fcf12080-f7e3-1067-bed2-21ffecf3ae64_is1`, display name 即我 (including Inno’s default version suffix/localized 版本 suffix), version 2.x, known `jotmo.exe` / `flutter_windows.dll` / `data/flutter_assets` / `unins000.exe` layout, and valid Authenticode signatures from `Senqisi (Wuhan) Technology Co., Ltd.` on the launcher. Historical `NotSigned` Inno uninstallers are accepted only with the verified registration/layout and `Setup/Uninstall` / 即我 PE identity; invalid signatures or other publishers remain rejected. Their hashes are captured and checked before retirement and recovery. The uninstaller is inspected, never executed.

HKCU is inspected once because its uninstall keys are shared across WOW64 views; both HKLM registry views are inspected. Existing Arkme keeps its registered scope and directory. Same-scope pairs remain supported. Mixed scopes require the same elevated Windows user and an existing registered Arkme: current-user Flutter can migrate into an all-user Arkme outside the current profile; machine-wide Flutter inside Program Files or the current profile can migrate into current-user Arkme only when there are no other non-special Windows user profiles. Unknown profile inventory, another user's source path, multiple installations, scope ambiguity and unknown layouts abort before replacement. Processes belonging to another Windows user are never closed by this helper. NSIS preserves the selected scope across UAC and requests elevation when protected recovery remains after the Flutter registration is gone.

New transactions that retire machine-wide Flutter into a user installation place recovery metadata and program backups under administrator/SYSTEM-protected `%ProgramData%\Jiwo Installer Transactions\<SID>-<destination hash>`. The record schema remains 2; its location is derived from the current SID and destination. Conflicting local/protected records stop recovery. Old supported local records remain discoverable. Cross-volume file replacement copies to a verified temporary sibling on the destination volume before atomic replacement; newly created files inherit destination access rights. Known interrupted temporary copies are validated before any rollback.

Preflight requires Windows 10/11 on native x64, refuses a higher installed version or build independently (same-version reinstall remains supported), and checks free space for staging, the cached installer, the new program, recovery backups, and atomic restoration scratch on their respective drives. New registrations persist `JiwoVersionCode`; old four-part DisplayVersion/PE build revisions are also checked. Flutter's validated Inno DisplayVersion and the signature-verified launcher's PE revision are compared with the incoming release. A zero/missing PE revision provides no authoritative Flutter build code; the release operator still must verify the highest published build across both product lines. Dynamic production `node.exe` kernels under `Arkme Harness` or the verified program directory are waited on; unrelated Node processes and `Arkme Harness Test` are excluded.

For Flutter migration the new app is installed in a separate directory. For both clean installs and existing Arkme upgrades, NSIS first extracts the new package into its private staging directory, verifies it, then overlays only manifest-listed files into the selected destination. Unknown destination files are never removed. The signed installer carries a SHA-256 manifest of every file from `afterSign`; before legacy retirement every installed file is checked and `arkme.exe` is verified against the publisher. Graceful window-close requests are followed by bounded waiting. A surviving app/kernel aborts installation; neither `taskkill` nor process termination is used by the migration script.

Retirement disables only the verified legacy `jotmo.exe`, `unins000.exe`, and exact target-matching standard shortcuts by renaming them with `.jiwo-v3-retired`. All Flutter local data, kernel files, assets and unknown files remain in place. After the commit marker is durable, recorded retired launchers/uninstallers are hash-checked as a complete set and removed. Cleanup failure preserves the journal for a later retry without rolling back the committed app. A subsequent Flutter reinstall at the original active path is never removed by this cleanup. This intentionally retains more files than a full cleanup: deleting broad Flutter `data`/`kernel` trees is unsafe. Only the exact Inno uninstall registry key is removed after payload and new NSIS registration verification. The persisted journal is then marked committed; interruption between these two steps restores the saved Inno registration and launcher on the next run. No uninstall command or directory-wide delete is used.

Shortcut reconciliation uses the journal's original snapshot, not the intermediate builder result. The production builder template changes shortcut AUMI/uninstall properties only when renaming an old shortcut succeeds. If an existing Flutter 即我 shortcut causes a rename collision, both links remain unchanged until journal-aware reconciliation; interruption at that boundary can restore the original bytes. On upgrades, a previously present desktop/menu entry becomes one verified 即我 entry pointing to the new `arkme.exe`; an originally absent entry stays absent. A fresh install keeps the defaults chosen by NSIS. Existing Flutter/Arkme startup entries are retargeted to 3.0, but startup is never newly enabled. Unknown same-name targets or arguments abort without overwriting them. New links are staged and verified before replacing an old entry, and the old `arkme.lnk` alias is removed only after the new target verifies. Desktop/menu AUMI is restored by NSIS after reconciliation. The original shortcut bytes remain part of the same rollback journal, including the current user's Startup folder during all-users migration.

Before overlay, the installer backs up each colliding known program file, old/new standard shortcuts, and the exact owned NSIS/protocol registry trees. The fixed journal records the original transaction's version/build, old and incoming SHA-256 values, legacy launcher ownership, and release registration metadata before any overwrite. Payload and backup files are flushed in the transaction directory before the active marker is saved. Each live program file is then replaced by an atomic same-volume move/replace, so an interrupted staging copy cannot truncate the live file. Rollback uses the same atomic approach; shortcut restoration stages beside its destination so a custom program drive is supported. Unknown files remain in place. The old Electron uninstaller is never called; its internal filename remains `Uninstall arkme.exe`, and its old bytes are backed up before the signed replacement is overlaid. The new uninstaller is signed and copied from private staging.

A synchronous failure rolls back manifest files, shortcuts, and owned registration. A process interruption leaves the journal available to the next signed production installer, including a later version with a different payload manifest. Recovery uses the original journal's inventory rather than the incoming EXE's file list. Before restoring anything, it checks the complete affected scene: all live program bytes must be recorded old or transaction-new bytes; backups must match; shortcut targets/arguments, legacy active/retired files, and registry scopes/values must remain transaction-owned. Registry validation permits interrupted writes containing only exact old or expected transaction-new values and rejects newer/unknown registration. An unknown replacement aborts before any rollback mutation. The unchanged `arkme` protocol tree is restored only from its owned snapshot.

Preparing, active, committed and rolled-back records support repeated recovery/cleanup. Preparing cleanup also tolerates a second interruption while discarding incomplete backup/staging copies. Recorded `payload-N` slots inside the private transaction directory are disposable while preparing: only their reserved name, regular-file type and maximum expected size can be validated before a copy finishes. This exception does not extend to active payloads, verified old backups, live application files, or unrecorded scratch names. Terminal cleanup checks all remaining backups first and tolerates those already removed; an empty transaction directory left after the final journal deletion can be removed on retry, while a nonempty directory without metadata is preserved and rejected. On all-users installs the recovery directory must be owned/controlled only by Administrators, SYSTEM, or TrustedInstaller; parent replacement rights and each backup file ACL are also checked. Unknown files, links, malformed records, or incompatible schemas cause a safe abort. Cleanup deletes only enumerated transaction-owned files, never the program directory. A committed journal is retained until the next installer run cleans its known backups without reverting a later installed payload. This recovery flow is not a supported downgrade utility.

The first production release uses fixed journal schema 2. Schema 1 belonged only to the unpublished implementation draft; there is no shipped schema-1 upgrade/conversion path. Unknown schemas remain fail-closed.

## Validation and release gates

`pnpm exec vitest run tests/windows-migration` covers portable policy, actual installed electron-builder template ordering, test isolation, and real temporary-file retirement, durable journal transitions, atomic overlay/rollback interruptions, repeated recovery, backup integrity, later-EXE recovery, unknown/newer live-state preservation, and terminal cleanup. Injected shortcut-interface fixtures cover manual updates, Flutter/Arkme coexistence, absent-entry intent, startup, unknown targets, and failed shortcut creation. Set `ARKME_TEST_PWSH` to an available PowerShell executable to run the filesystem and full-journal cases on macOS/Linux; Windows additionally exercises Windows path rules. Full-journal fixtures substitute only platform path/signature/COM and registry I/O boundaries while exercising production ownership and registry-scope validation. They never write real registry entries or install/uninstall an app. PowerShell tests are skipped on non-Windows hosts without `ARKME_TEST_PWSH`. PowerShell 7 parsing and portable filesystem cases have been run on macOS; Windows PowerShell 5.1, registry, UAC and Authenticode still need Windows acceptance.

The actual migration NSIS macros were also compiled successfully with electron-builder’s checksum-verified NSIS 3.0.4.1 toolset, using a compile-only fixture that was never executed. Reproduce with `ARKME_TEST_MAKENSIS=/path/to/makensis NSISDIR=/path/to/nsis ARKME_TEST_NSIS_PLUGINS=/path/to/nsis-resources/plugins/x86-unicode node scripts/windows-migration-compile-smoke.mjs`. This verifies macro compilation, not a signed production package or Windows installation.

Before publishing, run the signed installer on disposable Windows VMs and capture logs for:

- clean install and existing Arkme 0.3.x upgrade, including unchanged GUID/custom install directory;
- genuine signed Flutter 2.x in HKCU and HKLM, both registry views, paths containing spaces/Chinese characters, custom directories;
- normal exit and app/kernel refusing to exit; no forced kill;
- extraction/hash/signature/permission failures; old launcher and all local data retained;
- interruption before retirement, during launcher/shortcut rename, and after final registry deletion; retry recovers or completes;
- unknown directories/files, local SQLite/WAL files and credentials: compare hashes before/after;
- unsigned/different-publisher/reparse/ambiguous legacy installs: abort;
- test installer: no Flutter migration.

macOS validation cannot establish Windows PowerShell 5.1 execution, UAC behavior, a full signed production NSIS build, Authenticode chain validation, or real install recovery. Those remain Windows release gates.

Installer PowerShell actions persist detailed errors, stage and elapsed time to `%TEMP%\jiwo-install-*.log`. Flutter `2.x.y+build` versions are compared using both the semantic version and build suffix.

The non-installing `scripts/windows-migration-uac-probe.mjs` builds a diagnostic using the production initializer, production install-mode page prologue and upstream per-user directory lookup. Launch it as an interactive limited user and approve UAC; it must report `inner=1`, `scope=CurrentUser`, the original Arkme directory and an elevated read-only PowerShell preflight. It must never call an installation or process-exit action. Results are `%TEMP%\jiwo-uac-probe-nsis.txt` and `%TEMP%\jiwo-uac-probe-result.json`.

## Running-app exit consent

The production helper lists verified running Jiwo 2.0 / Arkme processes and offers Cancel installation or Exit and continue. Cancelling stops before replacement. Flutter window-close only hides its window, so the helper opens the verified process's actual tray menu and selects its unique enabled application-exit item (including historical `退出`). It never guesses command IDs, selects logout, or force-kills a process. Arkme receives its normal window-close request. Executable identity is rechecked before either action. The helper waits for owned app/kernel processes to terminate and offers retry/cancel when they remain.

`tests/windows-migration/exit.ps1` covers empty lists, cancellation, confirmed exit, retries, native compilation, historical exit labels and logout rejection. On the Windows test machine, the production exit helper was exercised interactively with signed Flutter and Arkme running together: all eight observed processes exited and the final owned-process count was zero. This validates exit handling, not the complete installation/recovery acceptance matrix.

### NSIS confirmation visibility regression (r6)

`nsExec::ExecToLog` launches PowerShell hidden. The first native show of a WinForms dialog can inherit that hidden startup state even though `ShowDialog` is waiting. The production dialog queues an explicit native show after its first `Shown` event. Run `tests/windows-migration/dialog-nsis.ps1 -Makensis <verified makensis.exe>` on an interactive Windows desktop: it compiles a non-installing NSIS probe, invokes the production confirmation through the actual x86 PowerShell/nsExec chain, verifies native visibility, clicks Cancel and checks the false result. It neither installs files nor exits a real client. The same probe failed before the fix and passed after it.

Unknown same-name shortcuts remain protected. A start-menu link pointing into an earlier unpacked r2 test build caused the test machine's Apply phase to abort before journal creation or program replacement. That specific test artifact was backed up with a SHA-256 record outside the start menu, then removed from the conflicting location. This is test-environment cleanup, not a new production whitelist for arbitrary shortcut targets. Conflict errors now include the shortcut path, target and arguments.

The signed r6 test installer (3.0.0 / 277, SHA-256 `e06b69f99091ac9d8bf71d304e3b32f6bde7527f023f86d3260d5bf52d5e5d4b`) completed the real mixed-scope Flutter + Arkme migration on the Windows test machine with exit code 0 on 2026-09-22. Prepare took 6.0 s, Apply 39.5 s, Commit 5.0 s and Finalize 6.4 s. Payload hashes, Authenticode signatures, committed journal, new registration and desktop/start-menu/startup targets passed verification. The three captured data roots (Roaming/com.senqisi, Local/com.senqisi, Roaming/Arkme Harness) contained 268,762 entries before and after installation; paths, content SHA-256, file modes and symbolic-link targets matched exactly. Data-root ACLs also matched. Symlinks were recorded without traversing their targets. The installer was run elevated with `/S /currentuser` and did not launch the app afterward; first launch/runtime activation was not tested by this acceptance run. Evidence is retained under `release/windows-x64-r6/` locally and `C:\Users\w8758\jiwo-install-diagnostics-20260922` on the test machine.

The mixed-scope regression matrix includes both directions, other-profile rejection, registry hive restoration, source-scope shortcut intent, interrupted destination transfers and identical old/new payload hashes. `tests/windows-migration/protected-journal.ps1` is an elevated interactive Windows fixture for actual protected-directory ACLs and transferred-file user access. Full installation acceptance on additional Windows machines remains a release gate.

### Mixed-scope migration and retirement cleanup (r9)

The previous scope guard allowed only machine-registered Flutter located inside the current profile alongside per-user Arkme. A genuine Program Files Flutter installation was therefore rejected. Both mixed directions now retain the existing Arkme scope; moving from machine-wide Flutter to per-user Arkme requires a verified inventory with no other non-special user profiles. Machine-wide recovery ownership is stored under an ACL-protected ProgramData directory, even when the new app is per-user. Tests exercise both registry hives, source-scope shortcuts, interrupted transfers and protected-directory access.

A subsequent real-install preflight exposed two orphan `.lnk.jiwo-v3-retired` files from the earlier test migration. The old implementation never removed committed legacy retirements. The r9 cleanup validates every remaining retirement hash before removing any of them, preserves unknown replacements and the journal, tolerates previously removed entries, and never removes an active path created by a later Flutter reinstall. Three regression fixtures cover those cases. The two orphan test links, whose saved targets were the earlier desktop Flutter test directory, were hash-verified and preserved under `C:\Users\w8758\jiwo-retirement-evidence-r9` before removing only their conflicting paths. Production does not automatically accept or delete orphan files without an ownership record.

Signed r9 (`3.0.0 / 277`, EXE SHA-256 `7c2d4e45db4cfe45f0cca71fd6c33611fe12b4ece30ce8872de6ced255a646bc`) passed real machine-wide Flutter → existing per-user Arkme migration and a same-version reinstall on 2026-09-22, both exit code 0. The first run took 7.1 s Check, 6.4 s Prepare, 40.3 s Apply, 5.1 s Commit and 6.3 s Finalize. Installed payload hashes, signatures, registration and desktop/menu/startup links passed after both runs. Retired launchers were cleaned; the subsequent reinstall removed the prior protected migration journal and used a normal per-user journal for its own transaction. All 268,787 captured data entries matched before/after both installs (paths, SHA-256, file modes, symlink targets); root ACLs also matched. Tests ran elevated and silent without launching the app. Reverse scope is covered by policy, real HKLM lookup and rollback fixtures, not a complete reverse-scope installation on this machine. Artifacts and evidence are in `release/windows-x64-r9/`; the test machine desktop contains `Jiwo-3.0.0-277-Migration-Test-r9`.
